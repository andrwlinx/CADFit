- When the server reports a full context, halve the number of recent tool
  results kept in full and retry.
- Older turns are shortened entirely: tool output, assistant text and long
  string arguments (code) of old tool calls; the transcript keeps everything.
- If a reply contains a code block but no tool call, the nudge says the code
  was not run and to call `add_code`.

**Failures (no model).** 12 beam and 6 beamgwn parts; 3 parts fail in both
(00000839, 00000914, 00002402). Causes seen in the per-part logs:
- The run ended without `final_iou.json` (most of them): the search timed out

`bench/score.py` skips any part whose STL name appears in a running process,
so 4 runs were left unscored until the workers were killed. Fix needed:
kill the pool (process group) when a part times out.

- Watertight parts are now identical in both arms (repair skipped), and

**Remaining failures.** Beam 9, beamgwn 2, two causes:
- 6 beam parts (00000425, 00000493, 00000572, 00000742, 00000914,
  00002383): "No valid operations after evaluation"; see below.
- 3 beam parts (00000455, 00001458, 00002488) and both beamgwn failures
  (00000914, 00002402): the greedy step still hits its 3000 s timeout. The
  profile log shows it stalling in the backward removal pass (4 parts,
  right after the forward pass) or the cut phase (00000455), well past
  the pass's 1800 s budget; 3 of them report a dead pool worker first.
  Cause found 10-12 (below).

**New bug found: the target's alpha-wrap vs the 30 s watchdog.** In the 6
"no valid operations" runs every candidate scored IoU 0.000000 although it
built. Each eval worker alpha-wraps the open target on its first
candidate, inside the 30 s per-candidate SIGALRM watchdog. Unloaded the wrap
takes 17 s (00000493); with ~170 workers wrapping at once it overruns, the
alarm fires inside `_alpha_wrap_forked`, which read it as a failed wrap and
returned the open mesh; the target manifold was then cached as `None` and
every later IoU in that worker was 0. Standalone, the same part evaluates
204/261 candidates. Not new: §5 had the same signature on beam 00000572,
00001607, 00002383 and beamgwn 00002078; the repair arm mostly avoids it
because its target is already a closed solid (no wrap).

Fix (`iou.py`, `greedy_search.py`, `cadquery_ops.py`): build the target's
manifold once in the parent before the eval pool starts (`warm_manifold`;
forked workers inherit it, spawned ones build it in the pool initializer,
outside the watchdog), and re-raise a watchdog timeout from the wrap instead
of caching a failed target. Test: `bench/test_p3.py` 23/23 (the new check
fails on the old `iou.py` with IoU 0.000). 

**Cause of the remaining timeouts: `Pool.terminate()` deadlocks.** Step
output is now unbuffered, and the greedy step dumps all thread stacks to
`stack_dump.txt` on SIGUSR1. In the first re-run of the failed parts, the
two greedy steps still running after 25 min (beamgwn 00002383, 00000572)
were both inside `shared_pool.terminate()` at the end of the removal pass,
blocked in `multiprocessing.pool._help_stuff_finish` taking the task
queue's lock. terminate() waits there for stop sentinels a stuck pool never
delivers, so the step sat until its 3000 s timeout and lost the finished
search. Every pool exit (`with mp.Pool(...)`) goes through the same code.

Fix (`cadquery_ops.py`, `greedy_search.py`): `abandon_pool` stops the
pool's worker handler, kills the workers directly and cancels the pool's
exit finalizer; every greedy-step pool now uses it (`guarded_pool`, and the
removal pass's shared pool). Test: a pool whose queue lock is held by a
stuck process; terminate() hangs, abandon_pool returns at once
(`bench/test_p3.py` 24/24, Mac and workstation). CADBench 00014841: final
STL byte-identical to before (judge 0.9498).
